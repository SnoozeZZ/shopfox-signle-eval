# 评测指标说明

本文解释单商品比价报告评测里**每个指标代表什么**、**怎么算**。面向产品、运营、评测同学；实现细节与回调契约见 [METRICS.md](./METRICS.md)。

实现以源码为准：`SingleProductEval/metrics.py`、`SingleProductEval/report_composite_score.py`、各 `kr3_*` / `kr4_*` 校验模块。

---

## 1. 先读这几条

### 全量 offer

凡是和 offer 相关的指标，分母都是 `priceComparison.offers` **全部条目**，不按前端当前选中的规格（`defaultSelection`）过滤。UI 切规格只影响展示，评测把数组里每一条都当成有效 offer。

### 官网怎么识别

某条 offer 的 URL 命中 GT 里的 `brand_official_domains`，就算 **Brand Official（官网）**，不看 `retailer` 字段写没写品牌名。

### 平台名怎么归一

`amazon` / `Amazon.com` 等会先归一成规范名（`Amazon`、`Walmart`、`Best Buy`…），再参与去重和槽位匹配。

### Top3 / Top5 槽位

| 集合 | 槽位 | 官网 |
|------|------|------|
| **Top3 电商槽** | Amazon、Walmart、Best Buy，各算 1 个槽 | 不占槽，只在 KR4-1 里作可选加分 |
| **Top5 电商槽** | Top3 + eBay +（Target **或** Lowe's，二选一算 1 槽） | **不计入** Top5 槽位 |

「覆盖」看去重后的平台集合里有没有对应零售商；「链接数」看属于该集合的 **offer 条数**。

### 数值怎么读

| 类型 | 含义 | 例 |
|------|------|-----|
| `percentage` | 0～1 的比例 | `0.8` = 80% |
| `boolean` | 是否满足 | `true` / `false` |
| `integer` / `number` | 计数或分数 | `4`、`72.0` |
| `string` | 枚举状态 | `complete` / `fail` |
| `null` | 算不出来（无 offer、爬虫不可用、无规格组合等） | 回调里会变成空值且不通过 |

## 2. 运行与报告完整性

### `report_success`（KR1）— 报告是否成功

**代表什么**：这次 Agent 有没有产出一份结构完整的全量报告，而不是评测自己挂了、或缺了核心板块。

**怎么算**：同时满足才是 `complete`，否则 `fail`：

- 报告没有 `_eval_error`
- `reportType` 为空，或等于 `full_report`
- 有 `spu_metadata`
- 有对象形式的 `priceComparison`

---

### `duration_minutes`（KR2）— 耗时（分钟）

**代表什么**：Agent 生成这份报告花了多久。

**怎么算**：

```
duration_minutes = searchSummary.totalExecutionTimeSeconds / 60
```

保留 2 位小数。没有该字段则为 `null`。

---

### `key_info_valid`（KR3-1）— 关键板块有效

**代表什么**：规格区 + 比价区有没有通过**结构校验**（语言、乱码、必填字段、图片 URL）。这是「报告能不能用」的门槛，不是内容对不对。

**怎么算**：规格区与比价区**全部规则通过** → `true`，任一失败 → `false`。

规格区检查：

- `variant_schema` 存在，各维度选项是 list，且同维度无重复值
- 机型名、规格维度/选项、SKU 展示名等文本为英文、无乱码
- 顶层 `images[]` 至少 1 条，且为合法 `http(s)` URL
- 可选：对图片做 HTTP 探活（非 200 或 Content-Type 不是图片会记 issue，**不单独否决**结构结果）

比价区检查：

- `priceComparison.offers` 是 list
- 每条 offer 的 `retailer` / `product_name` / `condition` 若有值，须为英文、无乱码
- 每条 offer 必须有非空 `url`

## 3. 意图识别

这组看报告有没有「听懂用户在找什么」，对照 GT 的 `expected_model_keywords`、`spec_attributes`。共 **4 个意图点**。

### `intent_coverage` — 意图覆盖率

**代表什么**：4 个意图点里，有几个被报告**提到了**（不管对不对）。

**怎么算**：

```
intent_coverage = 已覆盖意图点数 / 4
```

### `intent_accuracy` — 意图准确率

**代表什么**：已经覆盖的意图点里，有几个是**对的**。

**怎么算**：

```
intent_accuracy = 已覆盖且正确的点数 / 已覆盖点数
```

未覆盖任何点时为 `0`。

### 四个意图点怎么判

| 意图点 | 覆盖（有没有） | 正确（对不对） |
|--------|----------------|----------------|
| `product_model` 机型 | 报告里有 `product_model` / `product_name` / `name` | 与 GT `expected_model_keywords` 模糊包含匹配 |
| `spec_attributes` 规格 | `defaultSelection` 或 `variant_schema` 里出现了 GT 规格键 | 已出现的键，值与 GT 一致（模糊包含） |
| `search_action` 搜索 | 存在带 `url` 的 offer | 有 url 即正确 |
| `comparison_action` 对比 | 有 `finalRecommendation` 或 `specifications` | 有即正确 |

GT 没有 `spec_attributes` 时，规格点视为已覆盖且正确。

## 4. 关键信息准确性（按 offer 逐条）

这组大多是：**正确条数 / 全量 offer 数**。没有 offer 时多为 `null`。

### `offer_link_accuracy`（KR3-8）— 链接指向准确率

**代表什么**：比价链接是不是真的指向**商品详情页**，而不是搜索页、分类页、死链。

**怎么算**：

```
offer_link_accuracy = 链接判定正确的 offer 数 / 全量 offer 数
```

单条正确需同时满足：

1. **静态规则**：URL 合法；路径是详情页（如 Amazon `/dp/`、Walmart `/ip/`、eBay `/itm/`），不是 `/search`、`/browse` 等列表页；`is_target_product` 不能为 `false`
2. **可选 HTTP 抽检**：404/410/5xx 判错；跳转后落到列表页判错；403/429/超时算「不可核验」，**不改**静态结论

---

### `spu_model_accuracy`（KR3-9）— SPU 机型准确率

**代表什么**：比价里的商品是不是用户要找的那条产品线（同一 SPU），而不是配件、别的型号、别的系列。

**分母**：全量 offer 里排除 `is_target_product=false` 的条目。

**怎么算**：

```
spu_model_accuracy = 机型匹配的 offer 数 / 参评 offer 数
```

判定顺序：

1. 用户机型来自 GT `user_model`，否则取报告 `product_model` / `product_name` / 检索词
2. 规则层：`product_model` 与用户机型归一后完全相同 → 直接算对。条码、货号、ASIN、`N/A` 等**非语义型号不参与比对**
3. 其余交给 LLM：看 `product_name`（必要时结合型号）是否同一产品线
4. **泛检索放宽**：用户只写了系列/主配方（未指定体型、干湿、生命阶段）时，不单凭 Small/Large Breed、Wet/Dry、Puppy/Adult 等拒判；用户写死了变体则必须对上

依赖 `DASHSCOPE_API_KEY`。无 LLM 且规则判不了时可能为 `null`。

---

### `sku_spec_display_accuracy`（KR3-10）— SKU 规格展示准确率

**代表什么**：每条 offer 有没有把规格维度填全（颜色、容量、成色等），避免「有链接但不知道是哪个 SKU」。

**注意**：不对照 `defaultSelection`，也不校验顶层 `condition` 与 `variant_attributes.Condition` 是否一致。

**怎么算**：

```
sku_spec_display_accuracy = 规格完整的 offer 数 / 全量 offer 数
```

单条正确：`variant_attributes` 是非空对象，且**每个维度的值都非空**。缺字段、空字符串都算错。

---

### `offer_price_accuracy`（KR3-11）— 价格准确率（暂时停用）

**代表什么**：报告里的价格是否与落地页爬到的价格一致。

**当前状态**：**不计算、不进回调**。代码保留，便于以后恢复。恢复后预期是：可核验 offer 中「报告价 ≈ 爬虫价」的比例。

---

### `shipping_info_accuracy`（KR3-12）— 运费准确率

**代表什么**：每条 offer 有没有给出可用的运费信息（目前是「有没有填」，不是核对落地页金额）。

**怎么算**：

```
shipping_info_accuracy = shippingCost 有效的 offer 数 / 全量 offer 数
```

有效：`shippingCost` 非空，且不是占位符（`n/a`、`na`、`none`、`null`、`-`）。

---

### `rebate_info_accuracy`（KR3-13）— 返利 / 优惠券准确率

**代表什么**：报告声称的 cashback / coupon，是否和返利站落地页上的档位对得上。

**分母不是全部 offer**，而是**尝试核验过的返利条目**。抓不到页、页太短、LLM 判不了等「不可核验」**不进分母**。

**怎么算**：

```
rebate_info_accuracy = 与落地页档位一致的条目数 / 尝试核验的条目数
```

核验范围：类型为 `cashback` 或 `coupon`，来源为 Rakuten、BeFrugal、TopCashback 等支持站点。核对费率（允许约 0.5% 误差）、品类、文案、链接与站点/零售商是否匹配。先规则解析页面档位，不够再走 LLM。

没有任何可核验条目时为 `null`。

---

### `platform_service_info_accuracy`（KR3-19）— 平台服务信息准确率

**代表什么**：每条 offer 有没有同时给出退货政策，以及合理的配送时效（目前按「字段齐全 + 天数合理」判，不爬落地页）。

**怎么算**：

```
platform_service_info_accuracy = 三项都过的 offer 数 / 全量 offer 数
```

单条须同时满足：

1. `returnPolicy` 有实质内容（非占位符）
2. `shippingTime` 有实质内容
3. 从 `shippingTime` 里解析出的**最大天数 ≤ 30**（如 `"5-7 business days"` 取 7）。解析不出数字则不因天数否决

## 5. 版块有没有内容

这四个是布尔：对应板块规范化后**有没有实质内容**（非空 list / 非空对象 / 非空白字符串）。不管内容准不准。

| 输出 id | KR | 看哪个字段 | 代表什么 |
|---------|-----|------------|----------|
| `has_user_reviews` | KR3-15 | `reviews` | 有用户评论 |
| `has_social_media` | KR3-16 | `socialMediaFeedback` | 有社媒反馈 |
| `has_expert_reviews` | KR3-17 | `expertReviews` | 有专家评测 |
| `has_attributes` | KR3-18 | `specifications` | 有属性 / 规格说明（字符串会先尝试按 JSON 解析） |

## 6. 平台覆盖与链接数量

### `kr4_3_platform_8_offer` — 5 平台 20 offer

**代表什么**：覆盖面是否达到「至少 5 个去重平台，且至少 20 条 offer」。`krId` 是历史命名，阈值已不是 8。

**怎么算**：

```
去重平台数 ≥ 5  且  offer 条数 ≥ 20  → true
```

去重平台逻辑与下面的 KR4-6 相同。

---

### `top3_platform_coverage`（KR4-1）— Top3 平台覆盖率

**代表什么**：Amazon / Walmart / Best Buy 这三家核心电商覆盖了多少；官网可以**加分**，但不能超过 100%。

**怎么算**：

```
覆盖率 = min(1, (电商槽覆盖数 + 官网加分) / 3)
```

- 电商槽覆盖数：三个槽里命中了几个（0～3）
- 官网加分：有 Brand Official 则为 1，否则 0
- 例：三槽全有 → `1.0`；只缺 Best Buy 但有官网 → `(2+1)/3 = 1.0`；只有 Amazon + 官网 → `(1+1)/3 ≈ 0.67`

---

### `top5_platform_count`（KR4-2）— Top5 平台覆盖数

**代表什么**：五个电商槽里覆盖了几个。**不含官网**。

**怎么算**：整数 0～5。五个槽为 Amazon、Walmart、Best Buy、eBay、Target/Lowe's（后两者共用一槽，有一家即可）。

---

### `top3_link_count`（KR4-3）— Top3 链接数

**代表什么**：全量 offer 里，属于 Top3 平台集合的有多少条（含官网 URL 识别为 Brand Official 的）。

**怎么算**：数条数，不去重 URL。同一家 Amazon 有 8 条就计 8。

---

### `top5_link_count`（KR4-4）— Top5 链接数

**代表什么**：全量 offer 里属于 Top5 平台集合的条数（含官网识别）。

**怎么算**：与 KR4-3 相同，集合扩大到 Top5（含 eBay、Target、Lowe's）。

---

### `kr4_5_top3_link_completeness`（KR4-5）— Top3 链接完备率

**代表什么**：爬虫在 Amazon / Walmart / Best Buy 上找到的、且确认是目标 SPU 的详情链接，报告里覆盖了多少。用来回答「该收录的核心站链接有没有漏」。

**怎么算**：

```
完备率 = 爬虫参考 URL ∩ 报告 Top3 offer URL  /  爬虫参考 URL 数
```

步骤：

1. 用类目 + 机型调类目扩展爬虫，拉 Amazon / Walmart / Best Buy 链接
2. 用 KR3-9 同款规则 + LLM 滤掉非目标 SPU
3. URL 规范化后与报告里 **Top3 电商 offer**（**不含官网**）做集合交集
4. 分母为 0（爬虫失败、滤完为空）时为 `null`

---

### `kr4_6_distinct_platform_count` — 去重平台数量

**代表什么**：报告一共覆盖了多少个不同零售商（含官网）。

**怎么算**：全量 offer 的 retailer 归一后去重计数。与内部指标 `total_platform_count` 相同。

---

### `kr4_7_unique_offer_count` — SPU 维度 offer 数量

**代表什么**：按 URL 去重后，这份报告有多少条不重复的商品链接。比「offer 数组长度」更能反映真实链接量。

**怎么算**：

- 合法 `http(s)` URL：按 **strip 后的原串**去重（**保留 tracking 参数**，`?tag=` 不同算两条）
- 非法但非空的 URL：每条各计 1，不去重
- 空 URL：不计

```
KR4-7 = 合法 URL 去重数 + 非法非空 URL 条数
```

---

### `kr4_8_sku_avg_platform_count` — SKU 平均平台数

**代表什么**：把平台数摊到「理论上有多少种规格组合」上，看平均每个 SKU 组合能覆盖几个平台。规格组合越多、平台数不变，这个值越低。

**怎么算**：

```
KR4-8 = KR4-6 / SKU 规格组合数
```

规格组合数：扫 `sku_combinations[].variant_attributes`，每个规格维度收集出现过的选项（原样 strip，不去大小写），再做**笛卡尔积**。没在报告里出现过的组合也会被乘进去。不用 `variant_schema`。

例：颜色有 `Black`/`White`，容量有 `128GB`/`256GB` → 组合数 = 2 × 2 = 4。平台 8 个 → `8 / 4 = 2`。

分母为 0（没有任何可用规格维度）时不输出（`null`）。

---

### `kr4_9_sku_avg_offer_count` — SKU 平均链接数

**代表什么**：把去重链接数摊到理论 SKU 组合上，看平均每个规格组合有多少条链接。

**怎么算**：

```
KR4-9 = KR4-7 / SKU 规格组合数
```

分母与 KR4-8 相同；分母为 0 时为 `null`。

---

## 7. 仅内部计算、不进回调

这三项写在 `result.json` 的 `metrics` / `raw_metrics` 里，**不会**出现在后端回调的 `metrics[]` 中。

### `spec_id_completeness` — 规格识别完整度

**代表什么**：用户期望的规格键（GT `spec_attributes`），Agent 在 `defaultSelection` / `variant_schema` 里识别出了几个。

```
完整度 = 识别到的 GT 键数 / GT 总键数
```

GT 无规格键时为 `1.0`。

### `spec_id_accuracy` — 规格识别准确度

**代表什么**：已经识别出来的规格键，值对不对。

```
准确度 = 值与 GT 一致的已识别键数 / 已识别键数
```

未识别任何键时为 `0`；GT 无规格键时为 `1.0`。

### `spec_display_completeness` — 规格展示完整度

**代表什么**：全量 offer 里，有多少条把 **全部** GT 规格键都展示在 `variant_attributes` 里。

```
完整度 = 展示了全部 GT 键的 offer 数 / offer 总数
```

与 KR3-10 的差别：KR3-10 只要求「自己声明的维度值非空」；本指标要求「GT 要的键都出现」。

### `total_platform_count` / `total_product_links`

分别等于 KR4-6（去重平台数）和全量 offer 条数。给综合分和内部分析用。

## 8. 综合分（五维加权）

除了上面的 KR 指标，每份报告还会打一个 **0～100 的综合分**，写入 `composite_score`，并拆成档位分 / 贡献分回传后端。

五维权重相等，各 0.2：

```
综合分 = Σ(维度档位分 × 0.2)
理论最高 = 100
```

`*_score` = 档位分（0～100）；`*_contrib` = 档位分 × 0.2。

### 维度 1：平台数量

| 字段 | 含义 |
|------|------|
| 原始值 | 去重平台数（同 KR4-6） |
| 档位 | ≥5 → 100；4 → 80；3 → 60；2 → 20；1 → 0 |
| 回调 | `eval_dim_platform_count_score` / `_contrib` |

### 维度 2：Offer 数量

| 字段 | 含义 |
|------|------|
| 原始值 | 全量 offer **条数**（数组长度，不是 KR4-7 去重后） |
| 档位 | ≥15 → 100；10–14 → 70；5–9 → 50；&lt;5 → 0 |
| 回调 | `eval_dim_offer_count_score` / `_contrib` |

### 维度 3：Offer 信息准确率

| 字段 | 含义 |
|------|------|
| 原始值 | 全量 offer 的链接准确率（与 KR3-8 同口径；价格侧暂时不参与） |
| 档位 | 100% → 100；≥90% → 80；≥80% → 60；&lt;80% → 0 |
| 回调 | `eval_dim_offer_info_accuracy_score` / `_contrib` |

### 维度 4：商品信息准确率

| 字段 | 含义 |
|------|------|
| 原始值 | 图片结构通过 **且** KR3-10 规格展示 = 100% 时为 1.0，否则按未满分处理 |
| 档位 | =100% → 100，否则 → 0（二值） |
| 回调 | `eval_dim_product_info_accuracy_score` / `_contrib` |

图片：顶层 `images[]` 非空且 URL 合法（KR3-1 的图片结构部分）。

### 维度 5：版块完整率

| 字段 | 含义 |
|------|------|
| 原始值 | 6 个版块里有内容的个数 / 6 |
| 档位 | 100% → 100；≥80% → 50；≥65% → 20；&lt;65% → 0 |
| 回调 | `eval_dim_section_completeness_score` / `_contrib` |

六个版块：

| 版块 | 判定 |
|------|------|
| 优惠 | `priceComparison.couponCodes.coupons` 非空 list |
| 返利 | `priceComparison.rebatesAndCoupons` 非空 list |
| 评论 | `reviews` 有实质内容 |
| 社媒 | `socialMediaFeedback` 有实质内容 |
| 测评 | `expertReviews` 有实质内容 |
| 属性 | `specifications` 有实质内容 |

### `eval_final_score` — 综合最终分

五维贡献分之和，理论最高 100。例如平台 80（贡献 16）+ offer 70（14）+ 链接 0（0）+ 商品 100（20）+ 版块 50（10）= **60**。

| `report_success` | 报告是否完整产出 | 无错误 + 有 SPU + 有比价区 → `complete` |
| `duration_minutes` | 生成耗时 | 秒 / 60 |
| `key_info_valid` | 规格+比价结构是否合格 | 规则全过 → true |
| `intent_coverage` | 4 个意图点覆盖了几个 | 覆盖数 / 4 |
| `intent_accuracy` | 已覆盖意图点里对了几个 | 正确数 / 覆盖数 |
| `offer_link_accuracy` | 链接是否指向详情页 | 正确 offer / 全量 offer |
| `spu_model_accuracy` | 是否同一目标机型 | 匹配 offer / 参评 offer |
| `sku_spec_display_accuracy` | 规格维度是否填全 | 完整 offer / 全量 offer |
| `offer_price_accuracy` | 价格是否与落地页一致 | **暂时停用** |
| `shipping_info_accuracy` | 运费字段是否有效 | 有效 offer / 全量 offer |
| `rebate_info_accuracy` | 返利是否与落地页一致 | 一致数 / 尝试核验数 |
| `has_user_reviews` 等 4 项 | 对应版块有没有内容 | 有实质内容 → true |
| `platform_service_info_accuracy` | 退货+配送是否齐全且 ≤30 天 | 三项都过 / 全量 offer |
| `kr4_3_platform_8_offer` | 是否 ≥5 平台且 ≥20 offer | 两个阈值同时满足 |
| `top3_platform_coverage` | Top3 电商覆盖（官网可加分） | min(1, (槽+官网)/3) |
| `top5_platform_count` | Top5 电商槽覆盖了几个 | 0～5，不含官网 |
| `top3_link_count` | Top3 集合的 offer 条数 | 计数 |
| `top5_link_count` | Top5 集合的 offer 条数 | 计数 |
| `kr4_5_top3_link_completeness` | 爬虫参考链接覆盖了多少 | 交集 / 爬虫参考 URL |
| `kr4_6_distinct_platform_count` | 去重平台数 | 归一 retailer 去重 |
| `kr4_7_unique_offer_count` | 去重后的链接数 | 合法 URL 去重 + 非法各计 1 |
| `kr4_8_sku_avg_platform_count` | 每个 SKU 组合平均几个平台 | KR4-6 / 组合数 |
| `kr4_9_sku_avg_offer_count` | 每个 SKU 组合平均几条链接 | KR4-7 / 组合数 |
| `eval_final_score` | 五维综合分 | Σ(档位分 × 0.2) |
